# 2026-10-23

## Transactional outbox / Telegram delivery

- Added `outbox_events` + immutable `outbox_attempts` tables; migration `0017_blue_zaladane.sql`, applied to dev PGlite DB.
- Enqueue is inside the same transaction as receipt, handover, return and deposit-return writes.
- Worker claims due events, sends plain-text Telegram messages, journals every attempt, backs off exponentially, dead-letters after `OUTBOX_MAX_ATTEMPTS`, and replays in a new epoch.
- Delivery is at-least-once; no network call inside a DB transaction; stale processing locks recover after 5 minutes; attempt fencing prevents an old worker from overwriting a newer claim.
- Owner/admin APIs: `GET /api/outbox`, `GET /api/outbox/[id]`, `POST /api/outbox/[id]/retry`, `POST /api/outbox/[id]/replay`, `POST /api/outbox/process` (worker secret or owner/admin).
- UI: `/notifications` client-only page with status filter, attempt journal, retry/replay, process queue; nav item owner/admin-only.
- Messages never include document numbers, phone or email. Financial messages say "Internal record — not a payment confirmation." Telegram never changes financial results.
- Worker CLI: `npm run outbox:worker` (`apps/web/scripts/outbox-worker.ts`), interval/batch envs.
